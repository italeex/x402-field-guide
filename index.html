Reading an x402 402 Response, and Four Ways to Check a Base Address

Practical field notes for anyone calling a paid API or about to send USDC. Every command and response here was captured against live endpoints — no invented output.

x402BaseRPCsecurity

The x402 protocol lets a machine pay for a single HTTP request instead of holding a card or an API key. It reuses HTTP status 402 Payment Required as the negotiation step. Most write-ups describe the protocol; the part that actually breaks people's clients is the shape of the response and how to sanity-check what you're paying. This page covers both, using a real seller.

Scope and honesty note. I do not have clients, traffic numbers, or revenue to report — this is a new page with a new domain and no promotion yet. Everything below is something you can re-run yourself in under a minute. Where I made a mistake, I say so.

1. What a 402 actually returns

A paid endpoint advertises itself. Here is a real request to a real Base seller:

curl -s -i -X POST https://apiacre.com/v1/crypto/base-contract-inspect \
  -H 'content-type: application/json' \
  -d '{"contract":"0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913","block_tag":"safe"}'

The response:

HTTP/2 402
content-type: application/json
content-length: 2
payment-required: eyJ4ND...fX19   (6284 characters, base64)
link: <https://apiacre.com/catalog/...?from=quote>; rel="service-desc"
link: <https://apiacre.com/try/...?from=quote>; rel="payment"
cache-control: no-store

{}
The body is {} — two bytes. Every instruction for completing the payment lives in the payment-required header. A client that parses the JSON body and looks for the payment terms will find nothing and conclude the endpoint is broken. It isn't. Decode the header.

Decoding it

# capture the header, strip the "payment-required:" prefix, base64 -d
curl -s -D - -o /dev/null -X POST "$URL" \
  -H 'content-type: application/json' \
  -d "$BODY" \
  | grep -i '^payment-required:' | cut -d' ' -f2- \
  | base64 -d | jq .

The decoded challenge has this structure. These are real values from the response above:

{

  "error": "Payment required",
  "resource": {
    "url": "https://apiacre.com/v1/crypto/base-contract-inspect",
    "mimeType": "application/json",
    "serviceName": "API Acre",
    "tags": ["crypto","evm","base","ethereum","contract"]
  },
  "accepts": [
    { "scheme": "exact",
      "network": "eip155:8453",
      "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
      "amount": "5000",
      "payTo": "0xa0BFa4f07281c9b248DC3AED2217836BcA24869B",
      "maxTimeoutSeconds": 300,
      "extra": { "name": "USD Coin", "version": "2" } },
    { "scheme": "exact",
      "network": "solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp",
      "asset": "EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v",
      "amount": "5000",
      "payTo": "B4CHWQeQn7GDLZD2aW6hpGG2bEseisBFLZYECA3HDLan" }
  ],
  "extensions": {
    "bazaar": { "info": { "input": {...}, "output": {...} }, "schema": {...} },
    "payment-identifier": { "info": { "required": false }, "schema": {...} }
  }
}
FieldWhy you care
accepts[].amountAtomic units. "5000" with name: "USD Coin" means 5000 × 10⁻⁶ = $0.005. Reading it as 5000 dollars is the classic error.
accepts[].networkCAIP-2 chain id. eip155:8453 is Base; the solana: entry is a second rail for the same price. Pick by where your funds already are.
accepts[].payToWhere money goes. Different per rail — this is the seller's revenue address.
maxTimeoutSeconds: 300Your authorization expires in 5 minutes. If your retry loop is slower, it fails with an expired signature, not with a helpful error.
extensions.bazaarA complete JSON Schema for the input and the output, plus a filled-in example. This is how an agent binds the call without scraping docs.
payment-identifierOptional idempotency key (16–128 chars). Send it on retries so a timeout doesn't double-charge you.

2. The polite path: a 405 that tells you everything

Before paying anything, GET the endpoint:

$ curl -s -i https://apiacre.com/v1/crypto/base-contract-inspect
HTTP/2 405
allow: POST
content-type: application/problem+json

{"type":"https://apiacre.com/problems/paid-api-requires-post",
 "title":"Paid API execution requires POST",
 "status":405,
 "detail":"Send the example as JSON with POST. The unpaid POST returns an x402 v2
           PAYMENT-REQUIRED challenge ... This GET made no payment and executed no
           service.",
 "request":{"method":"POST","contentType":"application/json",
   "example":{"contract":"0x833589...","block_tag":"safe"}},
 "purchase":{"endpoint":"...","method":"POST","protocol":"..."}}

That is an unusually good 405: a machine-readable description, the exact request body, and an explicit statement that nothing was charged. Well-designed paid APIs let you evaluate the offer before you buy it. Check for this — a seller who returns a bare 404 instead is hiding the terms.

3. Is the paywall real? Two curls

A 402 proves someone wrote terms, not that anyone enforced them. The classic failure is a server that checks only whether a payment header exists:

// this is a fake paywall
const paid = !!(req.headers['payment-signature'] || req.headers['x-payment']);
if (!paid) return send402();
// else: serve the product

Probe it. Same request, three times:

# 1. no header
curl -s -o /dev/null -w '%{http_code} %{size_download}\n' -X POST "$URL" -d "$BODY"

# 2. garbage header
curl -s -o /dev/null -w '%{http_code} %{size_download}\n' -X POST "$URL" \
     -H 'PAYMENT-SIGNATURE: totally-bogus-not-signed' -d "$BODY"

If you get 200 with real payload data on request 2, the paywall is decorative and the product is being given away free.

Result against the seller above

no header                            -> 402   content-length: 2
PAYMENT-SIGNATURE: totally-bogus...   -> 402   content-length: 2

The bypass does not work — this seller verifies the payment. Two caveats worth knowing: both responses are content-length: 2, so you cannot distinguish "correctly rejected" from "rejected for a different reason" by size alone. And a single seller is one data point: audit each endpoint you depend on, because enforcement is per-route code and one unguarded route in an otherwise honest API is still a free leak.

4. Before you pay anyone: four free checks on a Base address

You do not need a paid API to tell a contract from a scammer. Base's public JSON-RPC is free and read-only. USDC on Base is at 0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913.

Check 1 — is it a contract or an EOA?

curl -s -X POST https://base.drpc.org -H 'content-type: application/json' \
 -d '{"jsonrpc":"2.0","id":1,"method":"eth_getCode",
      "params":["0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913","latest"]}'
# -> "0x60806040526004361061005a5760003560e01c80..."

"0x" means an externally-owned account — a plain wallet, no code. Anything longer is a contract. A wallet posing as a contract address can still sign a transaction, so this is a necessary check, not a sufficient one.

Check 2 — has this address ever sent anything?

curl -s -X POST https://base.drpc.org -H 'content-type: application/json' \
 -d '{"jsonrpc":"2.0","id":1,"method":"eth_getTransactionCount",
      "params":["0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913","latest"]}'
# -> "0x1"

A nonce of 0x0 on a brand-new seller address is expected, not suspicious. But on an address claiming years of activity, a zero nonce is a contradiction.

Check 3 — read a token balance directly

# balanceOf(address) = 0x70a08231 + 32-byte padded address
curl -s -X POST https://base.drpc.org -H 'content-type: application/json' \
 -d '{"jsonrpc":"2.0","id":1,"method":"eth_call",
      "params":[{"to":"0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
        "data":"0x70a08231000000000000000000000000deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"},
       "latest"]}'
# -> "0x000...2710"

0x2710 = 10000 = 0.01 USDC (6 decimals — another easy place to be off by a million). Note what this address actually is: a burn sink holding a rounding error. A large-looking balance on an address nobody controls is not revenue.

Check 4 — history, and the trap that ruins it

The obvious way to see an address's history is a Blockscout API call:

curl -s "https://base.blockscout.com/api?module=account&action=txlist&address=$ADDR&sort=desc"
The rate limiter returns HTTP 200 with an empty result. I hit this live while writing this page — eight calls in a row to the same query: 
call 1..7  ->  {"message":"OK","result":[{...}]}
call 8     ->  {"message":"Too many requests. Increase limits now at
                     https://dev.blockscout.com","result":null,"status":"0"}

Look closely at that last line. It is not an HTTP error — the status code was 200. The body carries result: null. Write the obvious parser:

rows = d.get('result', []) or []      # null -> []
print(f"rows={len(rows)}")             # rows=0

and you have printed rows=0 for an address that demonstrably has thousands of transactions. Add retries with backoff and it still prints rows=0 — every attempt, confidently. That output reads as a real finding: this address has never been paid. It is a fact about your HTTP client.

The fix is one line: gate the parse on the status field.

if d.get("status") != "1":
    raise RuntimeError(f"explorer refused: {d.get('message')}")  # UNVERIFIED
rows = d["result"]

Apply the same discipline to your own stack. Three different zeros get collapsed into one and each closes a live conclusion:

Zero you seeWhat it actually means
Throttled API → rows=0Rate limit. Says nothing about the chain.
Exactly 10,000 rowsPage cap, not a total. Don't call it "all activity".
DNS failure → 000 / emptyTransport blocked. Mimics "host is dead".

When money is on the line, confirm across an independent path. Blockscout can refuse; Base JSON-RPC cannot. The RPC above returned a correct answer for the same address at the same moment the explorer was throttling me.

5. Run all four yourself

ADDR=0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913
RPC=https://base.drpc.org
USDC=$ADDR

post() { curl -s --max-time 20 -X POST "$RPC" -H 'content-type: application/json' -d "$1"; }

# 1. contract or EOA?
post '{"jsonrpc":"2.0","id":1,"method":"eth_getCode","params":["'$ADDR'","latest"]}'

# 2. nonce
post '{"jsonrpc":"2.0","id":1,"method":"eth_getTransactionCount","params":["'$ADDR'","latest"]}'

# 3. USDC balance (0x70a08231 + padded address)
post '{"jsonrpc":"2.0","id":1,"method":"eth_call","params":[{"to":"'$USDC'",
  "data":"0x70a08231000000000000000000000000deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"},
  "latest"]}'

# 4. history — GATE ON status, or you will invent a zero
curl -s "https://base.blockscout.com/api?module=account&action=txlist&address=$ADDR&sort=desc" \
  | jq 'if .status != "1" then "UNVERIFIED: \(.message)" else "\(.result|length) rows" end'
